## Decision: new small PR (three commits), not a contribution to #35488

- On main the model runner, the decode CUDA graph runner and `ScheduleBatch`
  reach HiSparse through `hisparse_coordinator is not None`, but the
  scheduler and the batch-result processor still test `--enable-hisparse`
  and then dereference the coordinator. `TpModelWorker.register_hisparse_coordinator`
  (added with HiSparse in #20343, no callers) can install a coordinator the
  runner drives and the scheduler ignores. Gating on the coordinator the
  scheduler holds is a behavior-preserving consistency change: the runner
  builds a coordinator exactly when `--enable-hisparse` is set.
- Real bug on main, fixed in the first commit: an abort that arrives while a
  request is in HiSparse staging (prefill done, host copy in flight, in no
  batch) is dropped, and the request decodes to completion. `abort_request`
  has a `# todo hisparse` comment at this spot; `record_weight_version_change`
  already adds staging requests by hand.
- #35488 ("[HiSparse] HiCache as the plugin logical KV pool", bingps): open,
  review required, last head commit 2026-09-16, CI red, 27 files and +4265
  lines. It adds a `HiSparseCoordinator` Protocol and a second backing but
  keeps every `enable_hisparse` gate. Engaging on it is publication, and
  stacking on a stale 4k-line PR would block this fix on its review. The
  change here is orthogonal and small; whichever lands second rebases
  mechanically (its new gates would test the coordinator too).
- Not included (rule 10): the QSA admission caps S05 (`get_num_allocatable_reqs`
  at most one request and the free lease count) and S06
  (`prefill_max_requests=1`). Upstream has no concept for them and #35488
  proposes `admit_budget()` instead; they stay plugin hooks. See the S06 note
  below.
- Scope rule: colocated prefill-to-decode paths gate on the coordinator. PD
  decode's direct-to-host path (`disaggregation/decode.py`, about ten sites,
  `scheduler_pp_mixin.py` `admit_request_direct`, the decode-mode
  waiting-queue abort in `abort_request`) is private-host specific and keeps
  the flag, as does configuration (pool sizing, `pool_stats_observer`,
  `dp_attn.py`, `ModelRunner.max_token_pool_size`). This set is exactly the
  set of sites the fork changed.

## Motivation

A HiSparse request whose prefill finished waits in the coordinator's
`ack_staging_queue` until its host copy lands; it is in no batch until
`collect_ready_reqs` returns it. `abort_request` only scans batches, so an
abort in that window (client disconnect, timeout, `abort_all`) is dropped and
the request decodes to completion. `abort_request` carries a
`# todo hisparse` note at this spot, and `record_weight_version_change`
already adds staging requests by hand.

Separately, the model runner, the decode CUDA graph runner and
`ScheduleBatch` reach HiSparse through `hisparse_coordinator is not None`,
while the scheduler and the batch-result processor test `--enable-hisparse`
and then use the coordinator. A coordinator installed through
`TpModelWorker.register_hisparse_coordinator`, or by a plugin hook on the
model runner, is driven by the runner but ignored by the scheduler.

## Modifications

- `Scheduler.collect_inflight_reqs` includes staging requests when a
  coordinator exists, so `abort_request` reaches them; the cancelled request
  still runs the usual cleanup decode step, like any running request with
  `to_finish` set. `record_weight_version_change` drops its manual copy of
  that union.
- `Scheduler.init_hisparse_coordinator` adopts the coordinator the model
  runner holds and registers the decode producer stream if there is one.
- The colocated prefill-to-decode paths test the coordinator instead of the
  flag: the staging collection and the skipped `last_batch` merge in
  `get_next_batch_to_run`, the pool checks in `on_idle`, staging in
  `is_fully_idle`, and staging admission and `request_finished` in the
  batch-result processor (its now-unused `get_memory` import is removed).
  PD decode's direct-to-host path (`disaggregation/decode.py`, the PP mixin,
  the decode-mode waiting-queue abort) and memory configuration keep the
  flag.
- With `--enable-hisparse` on or off nothing else changes: the runner builds
  a coordinator exactly when the flag is set.
- Tests (CPU, `register_cpu_ci`, existing files extended):
  - `test_scheduler_chunked_abort_race.py::TestHiSparseStagingAbort`: an
    abort reaches a staging request (fails on main).
  - `test_scheduler_chunked_req_gate.py::TestHiSparseCoordinatorGates`: the
    scheduler adopts a runner coordinator without the flag; staged requests
    replace the `last_batch` merge (both fail on main).
  - Six existing scheduler and batch-result tests get a
    `hisparse_coordinator` stub attribute (or stop patching `get_memory`).
  - The 43 unit-test files that build a scheduler or batch-result processor
    show no new failures relative to main.
