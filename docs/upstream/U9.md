### U9a: keep `req_generation` monotonic across `flush_cache`

- Main still resets the counter: `ReqToTokenPool.clear()` and
  `DecodeReqToTokenPool.clear()` call `self.req_generation.zero_()`.
  `HybridMambaDecodeReqToTokenPool.clear()` already does not, so the three
  pools disagree today.
- Upstream bug, independent of the plugin: `req_generation` tells the DSpark
  confidence relay whether a delayed confidence belongs to the row's current
  occupant (`dspark_planner._two_steps_prior_survival`: fresh iff the lagged
  generation equals the current one). Both stores of lagged generations
  survive `flush_cache`: `ConfidenceRelay.gen_ring`/`conf_ring` (owned by the
  scheduler's `FutureMap`) and the budget planner's `_carry_generation`
  (`DSparkWorkerV2.clear_cache_pool` is a no-op). After a flush the first
  occupant of a row gets generation 1 again, which equals the generation a
  pre-flush ring entry recorded for that row's first occupant, so stale
  confidence is accepted as fresh for the verify-token budget. Effect: a
  wrong speculative budget (speed, possibly batch shapes), not wrong tokens.
- The fork's reason (plugin lease owners keep generations to reject callbacks
  from released requests) is the same contract: a generation identifies one
  occupancy of a row.
- Related open PRs: #36093 (gate generation increments to DSpark; open since
  2026-08-23, stale against main's `alloc_rows`, CI red). Orthogonal and
  compatible: it changes when the counter is bumped, not whether it is
  reset. #34876 (O(1) `DecodeReqToTokenPool.alloc`) touches the neighbouring
  method only. #37932 mentions `req_generation` only in its description.
- Differs from the fork in one place: the fork left
  `DecodeReqToTokenPool.clear()` zeroing (inventory note 4.1). The upstream
  change fixes both pools; the target deployment (one TP2 server,
  `baseline.md`) does not use PD disaggregation, so plugin behavior is
  unaffected.

### U9b: set `multimodal_inputs` on the HiSparse staging-to-decode batch

- Main: `_build_hisparse_decode_batch` builds the batch with
  `ScheduleBatch.init_new` and never runs `prepare_for_extend`, so
  `batch.multimodal_inputs` is `None` (the function still ends with
  `# todo hisparse, maybe other info to contain for the new batch`).
- Upstream bug: HiSparse accepts multimodal classes
  (`Glm5NextForConditionalGeneration`, `MiniMaxM3SparseForConditionalGeneration`,
  `PixtralForConditionalGeneration`; `validate_hisparse`). For an M-RoPE
  checkpoint (`mrope_section` in `rope_scaling`), `ForwardBatch.init_new`
  calls `_compute_mrope_positions_decode`, which iterates
  `batch.multimodal_inputs`; with `None` it raises
  `TypeError: 'NoneType' object is not iterable` on the first decode step
  (reproduced on CPU with the real method; with the list it returns
  `seq_len - 1` for text rows and `delta - 1 + seq_len` for image rows).
  Without M-RoPE the field is unused at decode, so nothing changes there.
- No related open PR (`gh pr list --search` for `_build_hisparse_decode_batch`
  and `hisparse multimodal_inputs`: only closed #28121/#34077/#25915/#27370).
  The precedent is #28514 (populate `req_pool_indices_cpu` in the same
  builder) and its test, which this change extends.
- Identical to the fork's line.

### PR 1

Title: `[mem_cache] Keep req_generation monotonic across flush_cache`

```markdown
## Motivation

`req_generation` identifies one occupancy of a request-pool row: the DSpark
confidence relay accepts a delayed confidence only if the generation it
recorded equals the row's current generation. The relay's ring
(`ConfidenceRelay.gen_ring`/`conf_ring`) and the budget planner's carry ring
outlive `flush_cache`, but `ReqToTokenPool.clear()` and
`DecodeReqToTokenPool.clear()` reset the counter to zero. The first request
that reuses a row after a flush gets generation 1 again and can match a
pre-flush entry recorded for that row's first occupant, so its verify-token
budget is computed from another request's confidence.
`HybridMambaDecodeReqToTokenPool.clear()` already keeps the counter.

## Modifications

- `ReqToTokenPool.clear()` and `DecodeReqToTokenPool.clear()` no longer zero
  `req_generation`; allocation keeps incrementing it. Generation 0 still means
  "never allocated" (the planner checks `current_gen >= 1`).
- New CPU test `test/registered/unit/mem_cache/test_req_to_token_pool.py`:
  after `clear()`, every reallocated row has a generation greater than any
  observed before the clear, for both pools. It fails on main.

## Accuracy Tests

Not applicable: no kernel or model forward code changes, and no model output
changes.

changes.
```

### PR 2

Title: `[HiSparse] Set multimodal_inputs on the staging-to-decode batch`

```markdown
## Motivation

`_build_hisparse_decode_batch` builds the decode batch for requests leaving
HiSparse staging with `ScheduleBatch.init_new`, bypassing
`prepare_for_extend`, so `batch.multimodal_inputs` stays `None`. For M-RoPE
checkpoints (`mrope_section` in `rope_scaling`) among the classes HiSparse

positions by iterating that list and raises `TypeError` on the first decode
step; image requests would also lose their `mrope_position_delta`.

## Modifications

- Populate `batch.multimodal_inputs` per request in the builder, as
  `prepare_for_extend` does for colocated batches. Text-only rows stay
  `None`, so text decode is unchanged.
- New CPU test in `test_schedule_batch_req_pool_indices.py`
  (`TestHisparseDecodeBatchMultimodalInputs`): the rebuilt batch carries one
  entry per request in batch order. It fails on main. The existing builder
  test now shares the scheduler stub.

`mrope_position_delta`, as without HiSparse. An image/text M-RoPE decode
smoke test would add integration evidence.
```
