# U4: pool fixed reservation and `full_kv_pool` factory

Agent UC, Phase 3 Track U, 2026-10-08 (revised after G3-U review). Upstream
base: `upstream/main` `b7b2975b57`. Fork reference: `ee8fe158d6`.
Inventory rows: K01 (around), K02 (REPLACE), K03 (around + before), C01
(after), C02 (before).

## Decision: no upstream PR; K02 can shrink with an existing upstream seam at the next pin

- What the fork does: with `SGLANG_QSA_HISPARSE_V3=p2-offload`,
  `DefaultPoolConfigurator` reserves a fixed byte amount (raw staging pool,
  pending ring) before sizing the logical pool (C01, C02), and
  `_build_hybrid_linear_kv_pool` validates the bounded configuration, builds a
  smaller raw staging `MHATokenToKVPool` (`size = slots.raw_pool_size`, page
  64, the cache dtype, the full-attention layer count, no quant method, no
  copy stream) and passes it to `QSATokenToKVPool` as `full_kv_pool`
  (K01-K03). Everything is gated on the offload runtime.

### K02 against the merged pool-class seam (#35594)

- Correction: #35594 ("Thread vendor KV pool classes through the in-tree
  builders", `c892301ff7`) is **merged** on main (2026-10-07), after the pin.
  `_build_token_to_kv_pool` now resolves `mha_pool_class` through
  `KVCacheConfigurator._resolve_kv_pool_class(kind="mha", ...)`, which asks
  `current_platform.get_kv_pool_cls(kind=...)` and accepts any subclass of
  `MHATokenToKVPool`. `_build_hybrid_linear_kv_pool` passes that class as
  `full_kv_pool_class` to `QSATokenToKVPool`, and `HybridLinearKVPool`
  constructs the full-attention pool from it (`full_kv_pool_class` already
  existed at the pin; the resolver is new).
- So no new prebuilt-pool factory is needed upstream. At the next pin the
  plugin can replace the K02 REPLACE with a narrow hook: an `around` on
  `KVCacheConfigurator._resolve_kv_pool_class` that, for `kind == "mha"` with
  p2-offload active, returns a plugin `MHATokenToKVPool` subclass whose
  `__init__` substitutes the staging size for the logical `size` it receives
  and runs K02's validation. Equivalence points to establish in that pin
  cycle (they are why this is not claimed yet):
  1. constructor arguments: the class path passes `enable_kv_cache_copy`
     (False when speculative decoding is off, which C01 requires) and
     `quant_method` (K02 requires None), and `post_capture_active` only when
     active (K02 rejects it); the fork's prebuilt pool used the defaults,
     which match;
  2. scope: the resolver serves every MHA pool built in
     `_build_token_to_kv_pool`; the hook must apply only to the QSA hybrid
     pool under p2-offload;
  3. the staging size needs `max_running_requests`, which K01 currently binds
     from `sizes` around `_build_token_to_kv_pool`; the subclass could read it
     from the published schedule config instead (C01 already does), which may
     make K01 unnecessary;
  4. main's `_supports_fused_kv_pool` requires `type(storage) is
     MHATokenToKVPool`, so a subclass disables the fused decode KV path. That
     path needs FlashInfer trtllm decode (SM100/SM120), so it is inactive on
     the SM89 target, but the difference must be recorded.
- K03 (forward `full_kv_pool` through `QSATokenToKVPool.__init__`) becomes
  unnecessary on that route.

### Fixed reservation (C01, C02)

- Upstream's configurator is already coeff + bias (`DSV4PoolConfigurator`
  uses a bias), but `DefaultPoolConfigurator` exposes no way to add a fixed
  term. Proposing one now is a scope and maintenance judgment against it: the
  only user would be out of tree, the term's meaning (which pools it prices)
  is the plugin's, and the area is under active rework (#39614 QSA indexer
  dtype and cell size, #40743 MiniMax HiSparse full-pool accounting, #41325,
  #40227, open #38644 declarative pricing for hybrid pools). C01/C02 are
  already narrow `after`/`before` hooks, so the plugin gains little. Revisit
  if #38644 lands (a priced component would be the natural form) or an
  in-tree offload runtime for QSA appears.
