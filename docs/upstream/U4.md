## Decision: drop for now; no branch

- What the fork does: with `SGLANG_QSA_HISPARSE_V3=p2-offload`,
  `DefaultPoolConfigurator` reserves a fixed byte amount (raw staging pool,
  pending ring) before sizing the logical pool (C01, C02), and
  `_build_hybrid_linear_kv_pool` builds a smaller raw staging
  `MHATokenToKVPool` and passes it to `QSATokenToKVPool` as `full_kv_pool`
  (K01-K03). Everything is gated on the offload runtime.
- Upstream would need two generic seams: a fixed-bytes term (`bias`) for
  `DefaultPoolConfigurator` (upstream's coeff+bias model allows it; only
  `DSV4PoolConfigurator` uses a bias today) and a way to supply a prebuilt
  full-attention pool to the QSA pool (`HybridLinearKVPool` already accepts
  `full_kv_pool`; `QSATokenToKVPool.__init__` does not forward it).
- Neither seam has an in-tree consumer. The only in-tree callers that pass
  `full_kv_pool` build `UnifiedHybridLinearKVPool` (unified memory), never the
  QSA pool, so the missing pass-through is not an upstream bug. A seam with
  no user fails the unit-test admission rule and PLAN rule 10, and a
  pass-through alone (K03) would not remove the only REPLACE here (K02 must
  construct the pool mid-function).
- The area is under active rework: #39614 (QSA indexer dtype in
  `QSATokenToKVPool.__init__` and the QSA cell size), #40743 (MiniMax HiSparse
  full-pool accounting), #41325, #40227, open #38644 (declarative pricing
  table for hybrid pools) and #35594 (`_resolve_kv_pool_class(kind=...)`). A
  plugin-motivated seam now would likely conflict with #38644/#35594.
- Revisit when either an in-tree HiSparse/offload user of QSA exists or
  #38644/#35594 land; the fixed reservation then fits as a priced component
  and the staging pool as a resolved pool class or factory.
