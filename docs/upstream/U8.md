### Marlin MoE

- Bug on main: with `--enable-deterministic-inference` (which enables
  batch-invariant mode in `ModelRunner`), a token's Marlin MoE output still
  depends on the batch around it. `fused_marlin_moe` picks `block_size_m`
  from M, the native alignment places pairs within an expert bucket with
  cross-CTA atomics, bf16 on SM90+ (and fp16 everywhere) uses atomic-add
  reduction, and the kernel's split-K stripe partition (`iters =
  ceil(k_tiles * n_tiles * parallel / grid)`) follows the number of expert
  blocks. Not covered upstream: #42087 fixes QSA, HC and the shared-expert
  gate for the BF16 Qwen3.8 model, not Marlin; #39456 (OPEN) forces atomic add
  off for the dense Marlin GEMM only; #33511 (OPEN since 2026-08-04, CI red,
  does not apply to main) makes the align kernel's within-bucket order
  deterministic (run-to-run), which alone does not give batch invariance.
- Change (fork J01-J04, ported to main):
  - `marlin_template.h`: template flag `kDeterministicReduce`; when set,
    `iters = whole_k_stripe_iters(...)` so every output slice is reduced by
    one CTA over all of K in one order (new `stripe_schedule.h`, 21 lines,
    byte-identical to the fork).
  - `moe_wna16_marlin.cuh`: the flag threads through `get_marlin_kernel`,
    `determine_exec_config`, `marlin_mm`, `moe_wna16_marlin_gemm`; with it,
    `marlin_mm` uses a fixed launch shape (thread_k 64, thread_n 128, 128
    threads, 1 block/SM, the existing small-batch fallback config) and
    checks block size 8 without atomics. `is_valid_config` and the kernel
    lookup still run, so unsupported shapes fail loudly. One fork line was
    restructured to fit clang-format's 120 columns (same values).
  - `moe_wna16_marlin.py`: `use_deterministic_reduce` argument (JIT module key
    gains the flag; default False keeps the existing kernels).
  - `fused_marlin_moe.py`: when `is_batch_invariant_mode_enabled()`, block
    size 8, `moe_align_block_size_stable`, no atomic add, deterministic
    reduce. The fork tested `get_exec().deterministic.enable_deterministic_inference`
    (guarded by `is_config_namespace_published`); main enables batch-invariant
    mode exactly when that flag is set (`ModelRunner.maybe_enable_batch_invariant_mode`),
    and #42087 uses the same predicate. Deterministic mode takes precedence
    over main's newer single-token alignment path (#41251), as at the pin.
  - `moe_align_block_size_stable` (pure torch, no host sync) is added next to
    the native `moe_align_block_size` in
    `moe_runner/triton_utils/moe_align_block_size.py` instead of a new module;
    its body is byte-identical to the fork's `stable_align.py`.
- Note for review: with whole-K reduction a row's result should not depend on
  its position inside the sorted layout (rows of an MMA tile are independent
  and every slice has one owner), so the stable alignment may be numerically
  redundant. It is kept because the fork's GPU evidence covers exactly this
  combination; if #33511 lands, its `deterministic=True` Triton alignment has
  the same contract and can replace the torch version.

### QSA stable top-k (T01-T03): covered by #42087

#42087 ("Fix batch-invariant kernels for Qwen3.8 Flash-Next", OPEN, author
Misaka9468, review required, last update 2026-10-03, CI red) applies cleanly
to `b7b2975b57` (`git apply --check`). Under batch-invariant mode it calls
FlashInfer `top_k_ragged_transform(deterministic=True,
tie_break=TopKTieBreak.SMALL, dsa_graph_safe=True, row_starts=...)` in
`qsa_fast_topk` (all callers: prefill, `topk_transform`, decode) and skips the
JIT `fast_topk` decode shortcut. Contract equals the fork's
`_qsa_stable_topk`: exact top-k by score, smaller index wins ties, ascending
row-relative indices, `-1` padding. The validation interpreter's FlashInfer
0.6.18 has the same API (`TopKTieBreak`, `top_k_ragged_transform` with these
parameters; main pins 0.7.0.post1). Differences: CUDA only (HIP and CPU keep
the existing path); #42087 also fixes the QSA prefill launch config to
`(32, 4, 2)` in batch-invariant mode, which the fork does not. Contributing
would mean reviewing #42087 (publication); no patch is needed from us.

### Stable HC: dropped for the compiled-chain path; SM100 low-M path out of scope

The fork added a fixed-order split-K Triton kernel used by
`GatedResidual.mix(stable=True)`; at the pin the fused HC path was disabled
under deterministic inference and the torch.compile chain ran through an
unregistered `aten::mm.out`. #42087 registers a batch-invariant
`aten::mm.out`, which makes that chain batch-invariant without a second
kernel. On main `hc_mix_triton.py` moved to `kernels/ops/gemm/hc_mix.py`
(#41243) and the Qwen4-Exp decoder layers were rebuilt (the fork's
`mix(..., stable=)` call sites no longer exist).

Scope of that conclusion (`layers/hyperconnection.py` on main):
`GatedResidual.mix` has three paths. (1) On compute capability major 10
(SM100 family), for at most 24 rows, the CuTe split-K `hc_mix` kernel runs
whenever the shapes fit; it is not gated on deterministic inference. (2) The
persistent fused Triton kernel, which `fused_hc_mix_supported` disables under
deterministic inference. (3) The compiled chain. So under deterministic
inference the SM89 target (and every non-SM100 GPU) always takes (3), which
#42087 covers. On SM100 a batch crossing the 24-row boundary switches between
(1) and (3), and whether (1) itself is batch-invariant for 1 to 24 rows is
unverified; neither the fork (validated on SM89 only) nor #42087 addresses
it. That is a separate validation question for SM100 owners, not part of this
item.

## Draft PR body (upstream template; for owner review)

Title: `fix(moe): make Marlin MoE batch-invariant under deterministic inference`

```markdown
## Motivation

With `--enable-deterministic-inference`, Marlin MoE (GPTQ/AWQ/AutoRound int4
MoE models) is not batch-invariant: a token's output changes with the batch
it runs in, because the M block size, the atomic within-bucket placement,
atomic-add reduction (fp16 everywhere, bf16 on SM90+) and the split-K stripe
partition all depend on the batch. #42087 covers the BF16 Qwen3.8 kernels but
not Marlin; #33511 makes the alignment order repeatable but leaves split-K and
atomics.

## Modifications

- Marlin MoE kernel: `kDeterministicReduce` template variant; each CTA owns
  whole K slices (no cross-CTA split-K reduction) with a fixed launch shape
  (the existing small-batch fallback config).
- `moe_wna16_marlin_gemm(use_deterministic_reduce=...)`, default off.
- `fused_marlin_moe` in batch-invariant mode: block size 8, a stable (sorted)
  token alignment (`moe_align_block_size_stable`), no atomic add,
  deterministic reduce.
- Non-deterministic serving is unchanged (the default template argument
  instantiates the existing kernels).
- Tests: CPU oracle for the stable alignment; GPU case for bf16/fp16 that
  checks the dequantized reference, sub-batch invariance and graph replay in
  batch-invariant mode.
```
