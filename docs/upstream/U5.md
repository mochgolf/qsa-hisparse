# U5: decode CUDA graph backend lifecycle hooks, `req_pool_indices_cpu` for decode

Agent UC, Phase 3 Track U, 2026-10-08 (revised after G3-U review). Upstream
base: `upstream/main` `b7b2975b57`. Fork reference: `ee8fe158d6`.
Inventory rows: G01, G02, G03, R02 (REPLACE), F01 (hisparse `after` hooks,
deviation D3).

## Decision: defer both parts; no branch

### Graph lifecycle hooks (G01-G03, R02)

- What the fork needs from upstream: a capture context entered after
  `capture_prepare` (G01), a pre-fill hook and suppression of
  `num_real_reqs.fill_` in `DecodeCudaGraphRunner.load_batch` (G02), a replay
  scope inside `replay_session` and a hook right after `backend.replay`,
  before `_publish_read_done` (G03), and in `ModelRunner._forward_raw` a hard
  error when the QSA graph cannot run plus the same `num_real_reqs`
  suppression (R02).
- Every one of these is a call into the out-of-tree HiSparse runtime; the
  in-tree `HiSparseCoordinator` only needs `num_real_reqs.fill_`, which main
  already does in four places. Deferring is a scope, evidence and
  maintenance judgment, not a test-admission rule (protocol semantics would
  be admissible tests): upstream would carry five hooks whose only
  implementation lives out of tree, in a frozen file and a busy one, with no
  in-tree behavior to show reviewers, and the plugin keeps working with its
  REPLACEs meanwhile (PLAN rule 10).
- Where the hooks would live, and what they depend on. Two different things
  are in flight and should not be conflated:
  - U1 (agent UB's branch `qsa/U1-hisparse-coordinator-gating`) changes only
    the scheduler's gating from `--enable-hisparse` to coordinator presence
    and fixes a staging-abort bug. It introduces no protocol and no graph
    hooks; it neither enables nor blocks U5.
  - Open #35488 introduces a `HiSparseCoordinator` Protocol (not merged,
    stale, CI red). Graph hooks would naturally be protocol methods with
    no-op defaults, called by the runner where it already calls the
    coordinator. So U5's hooks depend on #35488 (or another protocol PR)
    landing first, not on U1.
  Either way the change touches `model_runner.py`, a frozen
  orchestration-only file (`.claude/skills/large-class-style`), plus
  `decode_cuda_graph_runner.py` (17 commits since the pin, open
  #28763/#41584/#42292 in the same area).
- Revisit after a coordinator protocol merges: propose `on_graph_capture`,
  `before_graph_replay`, `graph_replay_scope`, `after_graph_replay` and a
  `requires_graph_decode` property on it, in one PR, with the in-tree
  coordinator implementing them as no-ops.

### Widen `ForwardBatch.req_pool_indices_cpu` to decode (F01)

- Main (#39695, merged 2026-09-20) already has the field, set only for
  non-speculative extend ("Fresh only for non-speculative extend; speculative
  modes use device slots"). Its only readers are extend-time DSA KPool
  planning, prefill CUDA graph padding and two-batch-overlap splitting.
- The fork reads it in decode (`QSAHiSparseRuntime.begin_batch`). Upstream
  has no decode reader: the in-tree HiSparse coordinator takes
  `req_pool_indices_cpu` from `ScheduleBatch` in `prepare_for_decode`, and no
  attention backend copies `req_pool_indices` to the host during decode
  (searched `srt/` for `.cpu()`, `.tolist()`, `.item()` on it).
- The minimal change would be, in `ForwardBatch.init_new`:

  ```python
  req_pool_indices_cpu=(
      batch.req_pool_indices_cpu
      if batch.forward_mode.is_extend_without_speculative()
      or (batch.forward_mode.is_decode() and batch.spec_algorithm.is_none())
      else None
  ),
  ```

  plus a comment update and a test that a non-speculative decode batch
  carries the mirror. `ScheduleBatch` keeps it fresh across
  `filter_batch`/`merge_batch` (rebinding, not in-place), overlap scheduling
  already relies on it for decode (`overlap_utils.py`), and TBO splitting and
  DP padding already handle the field. Speculative decode must stay excluded
  (the mirror is stale in the draft window).
- Not prepared as a branch (scope judgment): a test of the widened field
  would be admissible as field-lifecycle bookkeeping, but upstream would gain
  no in-tree behavior from it, and the plugin row it would remove (F01) is
  already a narrow `after` hook pair (deviation D3), not a REPLACE. Bundle it
  with the first upstream decode consumer (for example the protocol
  follow-up above).
