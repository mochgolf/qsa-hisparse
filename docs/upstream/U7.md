### Z01 (`size_k`): w13 scales are permuted with the wrong K

- `GPTQMarlinMoEKernel.process_weights_after_loading` passes
  `size_k=layer.intermediate_size_per_partition` for the w13 (gate/up) scales,
  whose K is `hidden_size`. `marlin_permute_scales` uses `size_k` only for
  `group_size < size_k`, choosing the grouped or the channelwise ("single")
  permutation. The kernel (`kernels/ops/moe/moe_wna16_marlin.py:99-108`)
  treats any scale table with more than one group as grouped. So when
  `intermediate_size_per_partition <= group_size < hidden_size` the grouped
  table gets the single permutation. `check_moe_marlin_supports_layer`
  accepts `intermediate_size_per_partition == group_size` (for example
  `moe_intermediate_size=512` at TP4 with g128). This was derived from the
  code and shown on CPU (the permuted tensor differs); not GPU-verified.
- The fork's formula (`w13_scales.shape[1] * group`) mirrors the w2 call six
  lines below and is behavior-identical to `hidden_size` for grouped scales.
  For the target (g64 after the split, 320 per rank) both versions pick the
  grouped permutation, so this is a latent upstream bug, not a target fix.
- Not in #35955 (it does not touch `gptq_kernels.py`). Stacked on it to
  extend its new test file instead of creating a competing one.

### Z01 (`gc.collect()` / `empty_cache()`): not proposed

The fork calls `gc.collect()` and `torch.cuda.empty_cache()` after the w13
qweight, w2 qweight and w2 scale repacks of every MoE layer. Upstream would
ask for load-time peak memory numbers, which we do not have, and the calls
add a full GC per layer on every platform's load path. The plugin keeps
this behavior. Plugin-side option for the orchestrator (not done here): once
the `size_k` fix is upstream, Z01's 91-line REPLACE reduces to "run GC after
`replace_parameter` for `w13_qweight`, `w2_qweight`, `w2_scales`", which an
`after` hook on `gptq_kernels.replace_parameter` filtered by those names
could express (the linear kernel uses other names).

### Z03/Z04: Marlin g64 for g128 groups split by TP

- Main: an AutoRound g128 MoE layer whose per-rank intermediate size is a
  multiple of 64 but not of 128 (640 at TP2 for the target; also 768 at TP4
  and 1536 at TP8, i.e. Qwen3-30B-A3B and Qwen3-235B-A22B int4 g128) fails
  `check_moe_marlin_supports_layer` and falls back to `MoeWNA16` (Triton),
  which already loads such shards correctly by halving the group size and
  repeating scale rows (`group_size_div_factor`). So upstream is correct
  today; the change is a performance (and, for the fork, deterministic
  Marlin) path, not a bug fix.
- A g128 group is exactly two g64 groups with the same scale and zero point,
  so Marlin g64 with every checkpoint scale/qzero row loaded twice is exact.
  Only 128 to 64 can help: Marlin requires `intermediate_size_per_partition
  % max(64, group_size) == 0`.
- Upstream-style version (differs from the fork's mechanism, not its
  behavior on the target):
  - `GPTQMarlinMoEMethod(quant_config, *, scale_group_repeats=1)`; when > 1,
    `create_weights` wraps the `weight_loader` of `w13_scales`, `w2_scales`,
    `w13_qzeros`, `w2_qzeros` with `repeat_interleave(repeats, dim=-2)`
    before the FusedMoE loader shards them. No flag on `FusedMoE` and no
    `getattr` probing (the fork sets `layer._marlin_g64_expand_scales` and
    reads it with `getattr` in `FusedMoE.weight_loader`).
  - `AutoRoundConfig.apply_gptq_quant_layer` retries g64 only when the
    quant type passed the Marlin type check. The fork retries whenever
    `use_marlin` is false, which would also put asymmetric or unsupported
    types on Marlin; the target is a symmetric W4A16 checkpoint (the fork
    serves it on Marlin, which supports only `uint4b8`/`uint8b128` here).
  - Depends on #35955: with main's w2 scale sizing (`I * tp`), the loader
    shards the expanded table with the wrong size. Hence the stack.
- No related open PR: `auto_round.py` PRs #41877 (grouped names) and #42119
  (AMD Triton INT4, linear only) do not split groups; searches for AutoRound
  or Marlin MoE group/TP splits found nothing open.
- Not covered: native GPTQ checkpoints (`GPTQMarlinConfig.get_quant_method`
  returns Marlin for MoE without a shape check); out of scope here.
- Required before opening: GPU speed numbers (Marlin g64 vs MoeWNA16, e.g.
  Qwen3-30B-A3B AutoRound int4 at TP4, decode and prefill) and a GSM8K run;
  both need a GPU window and were not run (CPU-only phase).

### INT8-row PLE: dropped for this cycle

- Not upstream (main PLE tables are bf16/fp8). The fork's other E03 change,
  building the offloaded table on `meta`, is already upstream (#39928,
  merged 2026-09-20, main only).
- Upstream rewrote the PLE offload since the pin (`Qwen4ExpPinnedHostEmbedding`
  wraps a meta embedding, pinned or file-backed host tables via
  `qwen4_exp_ple_table.allocate_ple_host_table`, prefetch and RSS trimming,
  `_ple_table_is_fp8` with ModelOpt mixed precision), so none of the fork's
  E-hunks apply; it would be a re-implementation (about 150 lines) whose key
  test is a GPU Triton gather.
- Open #41624 ("Serve NVFP4-packed QAD checkpoints", L14nY1Wang; open, no
  reviews, last update 2026-09-29, no longer applies to `b7b2975b57`: conflict
  in `qwen4_exp.py`) adds the same plumbing for NVFP4 PLE: a quantized host
  table, a per-shard scale tensor loaded through the shard machinery as
  `shard_N.weight_scale`, and dequantization inside the offload gather. A
  separate int8 PR would conflict with it in every touched function, and
  upstream would want one quantized-PLE mechanism. The fork's format names
  its scales `shard_N.row_scale` and is selected by
  `ple_embedding_dtype="int8_row"` through a local `--json-model-override-args`
  on a locally converted table; there is no public checkpoint in that
  format. Choosing the upstream format (and possibly re-exporting the
  table) is an owner decision.
- Revisit when #41624 lands or is rebased: add `int8_row` as a second
  quantized-PLE format on its scale plumbing (`[rows, 1]` scales). Until
  then E03, E04, E06, E07, E08 stay in the plugin.

## Draft PR descriptions

### Suggested commit for #35955 (or follow-up PR after it merges)

Title: `fix: permute GPTQ Marlin MoE w13 scales over hidden_size`

#### Motivation

`GPTQMarlinMoEKernel.process_weights_after_loading` permutes the w13
(gate/up) scales with `size_k=intermediate_size_per_partition`, but their K is
`hidden_size`. `marlin_permute_scales` uses `size_k` to choose between the
grouped and the channelwise permutation, while the Marlin MoE kernel treats
any table with more than one group as grouped. When the expert partition is
not wider than one group (`intermediate_size_per_partition == group_size`,
which `check_moe_marlin_supports_layer` accepts, e.g. an expert width of 512
at TP4 with g128), the grouped w13 table gets the channelwise permutation.

#### Modifications

- Derive the w13 `size_k` from the scale table, as the w2 call already does.

#### Accuracy Tests

To run on GPU before opening: a GPTQ g128 MoE at a TP size where the expert
partition equals 128 (e.g. Qwen3-Next-80B-A3B GPTQ-Int4 at TP4), GSM8K
before/after.

#### Test plan

- `test_gptq_marlin_moe.py::test_marlin_moe_w13_scales_permuted_over_hidden_size`:
  w13 scales with two K groups and `intermediate_size_per_partition ==
  group_size` get the grouped permutation; fails before the fix.

### Split PR

Title: `[Quant] AutoRound MoE: run g128 experts on Marlin as g64 when TP splits a group`

#### Motivation

Marlin MoE needs whole quantization groups in every TP shard. AutoRound g128
MoE layers whose per-rank expert width is a multiple of 64 but not of 128
(640 at TP2, 768 at TP4, 1536 at TP8) therefore fall back to the MoeWNA16
Triton path. Each shard still holds whole g64 groups, and a g128 group is
exactly two g64 groups with the same scale and zero point.

#### Modifications

- `GPTQMarlinMoEMethod` takes `scale_group_repeats`; when > 1 it wraps the
  scale and qzero weight loaders so every checkpoint group row is loaded that
  many times before TP sharding.
- `AutoRoundConfig.apply_gptq_quant_layer`: if the quant type is
  Marlin-supported and the MoE layer rejects g128 but accepts g64, use
  Marlin with `group_size=64` and `scale_group_repeats=2`. Other layers are
  unchanged.
- Depends on #35955 (local w2 scale table without act-order).

#### Accuracy Tests

To do before opening: GSM8K for an affected checkpoint (e.g.
Qwen3-30B-A3B AutoRound int4 at TP4), Marlin g64 vs the current MoeWNA16
path.

#### Speed Tests and Profiling

To do before opening: decode and prefill throughput, same setup.

#### Test plan

  (selection, including the unchanged negative cases).
- `test_gptq_marlin_moe.py::test_split_group_scales_load_exact_tp_shards`
