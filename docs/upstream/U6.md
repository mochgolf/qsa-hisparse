### U6a: SM86/SM89 without classic FA2

- Bug on main: `_resolve_flash_attn_varlen_func` tries SM121, ROCm, classic
  FA2, then FA4 (`flash_attn.cute`). On SM86/SM89 with flash-attn-4 installed
  but no FA2, QSA decode selects FA4, whose SM80 tile for head dim 256 needs
  128 KiB of shared memory (SM86/SM89 have about 100 KiB); decode fails at the
  first request. #36968 (OPEN since 2026-08-29, last update 2026-09-14, CI
  red, review required, does not apply to main) reports the same failure on
  L20 (SM89) and proposes to reject the configuration before model load (+300
  lines, including an edit to the frozen `model_runner.py`).
- Fix: on (8, 6) and (8, 9), after the FA2 attempt and before FA4, resolve
  SGLang's vendored `sglang.kernels.ops.attention.flash_attention.flash_attn_varlen_func`
  (FA3 from sgl-kernel; upstream's own `_is_fa3_supported` states it is built
  for SM80/SM86/SM89/SM90a). Identical in placement and condition to the fork
  (Q01, fork commit `edd5f9b3c5`).
- Evidence the fallback works: the fork's target deployment is two RTX 4090
  (SM89, `docs/baseline.md`), and the Phase 2 validation interpreter has
  `flash-attn-4 4.0.0b19` and no importable FA2 (checked: `from flash_attn
  import flash_attn_varlen_func` raises ImportError), so the fork's eager and
  compat-only QSA decode in that environment runs through exactly this
  fallback (Phase 2 G2-2 fork runs; HiSparse graph decode uses the FlashInfer
  ragged wrapper instead). The FA3 loader (`flash_attention_v3.py`,
  `flash_attention.py`) is byte-identical at the pin and on main.
- Alignment with #36968: whichever lands second rebases mechanically (in
  #36968's resolver the SM89 rejection becomes a vendored-FA3 backend kind).
  Engaging on #36968 is publication and is not done.

### U6b: FP8 KV-cache scales

- Bug on main: with an FP8 KV cache and checkpoint KV scales
  (`layer.k_scale_float`/`v_scale_float` set by `BaseKVCacheMethod`), the QSA
  backend writes K/V without dividing by the scales and reads them back
  without multiplying, unlike the other attention backends. Values beyond the
  FP8 range saturate in the cache (PyTorch's cast saturates at 448: checked
  on CPU) and attention runs on the wrong magnitudes. Unit or absent scales
  are unaffected.
- Upstream history: #38855 (merged 2026-09-10, in the pin) fixed the FP8
  chunk-prefill crash with a plain cast and documented "the QSA backend writes
  the pool without per-tensor k/v scales". #36644 ("Fix FP8 KV cache support
  in QSA", OPEN since 2026-08-27, last update 2026-09-14, stacked on the old
  #36497 base, does not apply to main) is the origin of the fork's FP8 code
  (A01-A09, Q04, Q10 match it almost line for line): dtype validation,
  `KV_IS_FP8` kernel branches with in-kernel scales, `DEQUANTIZE_FP8` in
  `_compact_kv`. Its crash fix is superseded by #38855; its scale handling is
  what remains.
- Why a new, kernel-free PR instead of rebasing #36644:
  1. Main's backend has grown read/write paths #36644 does not cover: the
     fused decode KV path (`fused_kv_prepare`, writes and gathers FP8 without
     scales), context-parallel prefill (`_forward_extend_cp`), the HIP packed
     decode, the breakable-graph prefill path.
  2. Open #41933 (QSA maintainer, updated 2026-10-08) moves the FP8 to BF16
     conversion of the chunk-prefill K/V into a fused gather kernel. In-kernel
     scaling in `_sparse_gqa_chunk_prefill` (the #36644/fork approach) would
     then be dead code; folding the scales outside the kernels composes with
     it unchanged.
  3. Unit scales keep exactly the current code paths (no numeric change for
     existing FP8 users), which #36644's `KV_IS_FP8` accumulation rewrite does
     not (see "Plugin rows" below).
- Change (one file of logic, `qwen_sparse_attn_backend.py`, +74/-23):
  - `_kv_cache_scales(layer, kv_dtype)`: checkpoint scales for an FP8 cache,
    `(1.0, 1.0)` otherwise.
  - `_set_kv_buffer(pool, layer, loc, k, v)`: unit scales call
    `set_kv_buffer` as before; non-unit scales pass the scales and clones of
    K/V (the MHA pool divides in place, and first-chunk prefill and CP prefill
    still read K/V afterwards). Used by `forward_extend`, `forward_decode`,
    `_forward_extend_cp`.
  - Reads fold `k_scale` into the softmax scale and multiply the output by
    `v_scale`: chunk prefill, CPU reference paths, trtllm paged decode
    (`bmm1_scale`, `bmm2_scale`), FA varlen, HIP packed decode. CP prefill
    dequantizes the cached prefix (`.to(dtype) * scale`) because it is
    concatenated with unquantized new tokens.
  - `_try_fused_kv_attention` declines scaled FP8 caches (the fused kernel
    writes and gathers without scales).
  - Two comments in `qsa/sparse_attn.py` that stated "the backend writes the
    pool without per-tensor k/v scales" are updated (no code change there).
- Rejected alternative: assert unit scales (the DeepSeek-V4 trtllm backend's
  approach). Smaller, but it rejects checkpoints that other backends serve.

### Dropped parts

- QSA backend extension points for an out-of-tree offload runtime
  (`qsa_hisparse` attachment, `write_locations`, `prefill_slots`,
  `after_store`, `selected`, `capture_decode`, `begin_batch`, the SM89
  FlashInfer ragged FA2 graph wrapper): no in-tree consumer, so they fail
  upstream's test admission and rule 10; they also depend on the coordinator
  protocol (U1/#35488) that is not merged. They stay plugin patches.
- `decode_score_width` (Q05, T04): eager plain decode uses the batch's page
  table width as the MQA score stride, CUDA graph decode the maximum context.
  The TileLang/torch decode MQA computes each position independently of the
  width (checked in `qsa/mqa.py`), so only the native top-k collector order
  can differ, and under deterministic inference #42087's top-k reads only
  `[0, length)` of each row. Not an upstream bug; it stays a plugin row.

    scales, so dropping these rows changes FP8 chunk-prefill bits and needs

    upstreamed in any form.

### PR A

Title: `fix(qsa): use the vendored FA3 varlen kernel on SM86/SM89 without FA2`

### PR B

Title: `fix(qsa): apply checkpoint KV-cache scales on FP8 QSA caches`

Motivation: With an FP8 KV cache and checkpoint KV scales, the QSA backend
writes K/V without dividing by `k_scale`/`v_scale` and reads them without
multiplying, unlike the other attention backends; values beyond the FP8 range
saturate and attention uses the wrong magnitudes. #38855 made FP8 caches work
with unit scales; #36644 proposed scale handling on an older base.

Modifications: Scaled writes through `set_kv_buffer` (cloning K/V that the
pool divides in place), `k_scale` folded into the softmax scale and `v_scale`
applied to the output on every read path (chunk prefill, CP prefill, trtllm,
FA varlen, HIP, CPU reference), CP prefix dequantized before concatenation,
fused decode KV path limited to unit scales. No kernel changes; unit scales
and non-FP8 caches take exactly the previous code paths. Composes with #41933
(the gather converts FP8 exactly; scales stay outside the kernels).

Accuracy Tests: <owner: unit-scale identity and the scaled-cache comparison
from the GPU validation run.>

Speed Tests and Profiling: Unit scales: unchanged code. Non-unit scales: one
clone of K/V per write and one output multiply per layer.

Test plan: `test_qsa.py::test_qsa_decode_applies_fp8_kv_cache_scales` and the
`kv_scale=4.0` cases of `test_qsa_cp_unit.py` (fail before the change); GPU
items above.
